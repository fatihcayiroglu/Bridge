# P7 D1: partition decision, measured (2026-10-24)

**Recommendation: do not partition `messages`.** Partitioning by `HASH("channelId")` gives
no read benefit and costs:
- write throughput;
- lookup by id;
- global uniqueness of `_id`.

The scaling problem these measurements did find is **account erasure**. It scans `messages`
by `"userId"`, an unindexed column. Two ordinary indexes fix it, and partitioning would not.
This is an engineering recommendation with the evidence below. The owner records the
decision in the ledger (D1 row). Revisit it at the thresholds in the last section.

`P7_D1_PARTITION_ASSESSMENT.md` describes the read-only collector for a real installation.
This document answers what that collector cannot: measured latency, write cost and bulk
deletes, on a named dataset.

## Dataset: `d1-synthetic-chat`

No production database was available, so this is a **production-shaped synthetic dataset**.
It is not production data, and the limits section says what that leaves out. It was
generated by `server/scripts/p7-d1-scale-benchmark.cjs populate`, deterministic up to
`setseed(0.42)`, on a schema migrated by `main`'s own code with every production index
(including the trigram and full-text GIN indexes):

| | 2M scale | 6M scale |
|---|---:|---:|
| messages | 2,000,000 over 365 days, in time order | 6,000,000 |
| channels / servers / users | 20,000 / 1,000 / 50,000 | 50,000 / 2,000 / 100,000 |
| threads / thread replies | 20,000 / 200,000 | 50,000 / 500,000 |
| largest channel / median / p99 | 73,915 / 54 / 717 | 163,527 / 64 / 867 |
| share of messages in the top 1 % of channels | 21.6 % | 21.6 % |
| messages per author: median / max | 40 / 71 | 60 / 96 |
| `messages` with indexes | 1.3 GB | 3.7 GB |

Channel activity follows a power law: channel = 1 + ⌊C·u³⌋. 2 % of messages are
soft-deleted. Content is short synthetic text.

## Method

- PostgreSQL 16.15 with default settings, on a 4-vCPU / 15 GB VM shared by nothing else.
  The data fits in memory, so this is a **warm-cache** measurement.
- Latency is measured client-side over 400 samples per probe, after 20 warm-up queries.
  It uses the application's own SQL:
  - `MessageRepository.findByChannel`, first page and cursor page, in the row-comparison
    form that `pgCollection`'s `keysetRowComparison` actually sends;
  - lookup by `_id`;
  - member paging by server;
  - the thread page.
- Channels are chosen in proportion to activity ("activity-weighted") or uniformly.
- **Writes:** one writer's latency over 400 inserts, then four writers' throughput over
  10 s.
- **Bulk deletes:** each runs inside a transaction that is rolled back, so every layout
  deletes the same rows. A concurrent writer reports the worst insert latency during the
  delete. The rows are read once beforehand, so both layouts are timed warm.
- **Partitioned layout:** a copy of `messages`, `PARTITION BY HASH ("channelId")` with 16
  partitions and every index of `messages`.
  - Its primary key must become `("channelId", _id)`. A non-unique `_id` index is added,
    because without it lookups by id scan every partition.
  - Three unique indexes (`ackId`, `scheduledId`, the AutoMod alert) can only be unique
    per channel.
- **Two alternating rounds** (plain, partitioned, plain, partitioned) at each scale. The
  table gives both rounds.

A first pass, discarded, is recorded here because each fault would have biased the result:
- the plain layout was measured on a colder cache than the partitioned one;
- the first partitioned copy had no `_id` index;
- one probe used an OR-form cursor that the application never sends.

## Reading the results

- **Reads do not depend on table size here, and partitioning does not help them.** Every
  hot read is served by an index:
  - `idx_messages_channel_cursor ("channelId", "createdAt" DESC, _id DESC)` for channel
    pages;
  - the primary key for `_id`;
  - `members` and `thread_messages` indexes for the rest.

  From 2M to 6M the p50s stay within noise at about 1 ms. Partitioning adds about 0.25 ms
  to cursor pages (partition pruning, planning).
- **Partitioning costs.**
  - Lookup by `_id` is about 8× slower (0.2 → 1.7 ms) even with an `_id` index in every
    partition. Every partition must be probed, because the id says nothing about the
    channel. `findById` serves reports, pins, replies, reactions, edits and deletes.
  - Four-writer throughput is about 20 % lower at 6M.
  - `_id`, `ackId` and `scheduledId` uniqueness can no longer be global: idempotency keys
    and the scheduled-dispatch guarantee would hold only per channel.
- **Partitioning's one gain is bulk-deleting a very large channel:** 2.5–3.3 s against
  0.17 s at 163k rows. That channel's rows are spread across the whole plain heap but sit
  together in one partition. In the product this matters less than it looks:
  - **channel expiry** (D2's `channelExpiryWorker`) already deletes in bounded batches of
    500 rows per table;
  - only an owner deleting a very large channel in one transaction pays the 2.5–3.3 s.
    Concurrent inserts stalled at most 210 ms during it.
- **Account erasure is the operation that scales badly, on either layout.**
  `eraseAccountData` (lib/accountDeletion.ts, `prepareAuthorErasure` in
  lib/accountErasure.ts) runs, in one transaction:
  - a `replyTo` scrub whose `IN (SELECT _id FROM messages WHERE "userId" = $1)` scans
    `messages`;
  - a channel/avatar `SELECT … WHERE "userId" = $1`;
  - the anonymizing `UPDATE … WHERE "userId" = $1`;
  - the same for `thread_messages`.

  Measured with the real function, rolled back
  (`server/scripts/p7-d1-erasure-probe.ts`):

  | | 2M | 6M | 6M with the two indexes below |
  |---|---:|---:|---:|
  | Erasure, busiest author (anonymize) | 833 ms | 2,040 ms | **199 ms** |
  | Erasure, busiest author (admin purge) | 1,076 ms | 2,702 ms | **166 ms** |
  | Erasure, median author (anonymize / purge) | 801 / 1,013 ms | 1,934 / 2,719 ms | **168 / 162 ms** |

  It grows linearly with the table. At 60M messages, linear extrapolation gives roughly
  20–27 s in one transaction; that is an estimate, not a measurement. The indexes that
  remove it:
  - `messages ("userId")`: 41 MB at 6M, 0.7 % of the table;
  - `messages (("replyTo"->>'_id')) WHERE "replyTo" ? 'displayName'`: tiny;
  - `thread_messages ("userId")`.

  With them, four-writer throughput was **4,355 rows/s**, against 4,232–4,239 without:
  no measurable write cost. Building `messages ("userId")` took 4.9 s at 6M as a plain
  `CREATE INDEX`, which blocks writes for that long. This follows the 071 precedent
  (about a second per million rows), so a large installation should build it
  `CONCURRENTLY` out of band. That index change is proposed separately with its own
  migration and tests; it is not part of this document.

## Limits (what this does not show)

- **Synthetic data.** Real content lengths, attachment and embed mixes, reaction JSON,
  edit-history growth and real per-user skew differ. The 2 % soft-delete rate and the
  power-law channel skew are assumptions.
- **Warm cache, one VM.** Data larger than RAM, network-attached storage, replication lag,
  autovacuum under sustained churn and real connection counts were not measured.
- **Sizes up to 6M messages.** Index-backed reads showed no growth from 2M to 6M. That
  says nothing direct about 500M rows, where index depth, cache residency and vacuum
  dominate.
- **Hash partitioning only.** `RANGE` by month was not measured because nothing in the
  product deletes messages by age: there is no time-based message retention, and deletions
  go by channel or by author. If a time-based retention policy is introduced, `RANGE`
  partitions (dropping old months) become the relevant design and must be measured then.
- **No production run of the read-only collector.** `p7-partition-assessment.cjs` against
  a real installation remains the way to check that its sizes and plans resemble this
  dataset.

## When to revisit

Revisit partitioning, measured again with these scripts at the new size, if any of these
holds:
- `messages` exceeds about **100M rows**, or a single node's working set no longer fits in
  memory;
- a **time-based retention** policy for messages is adopted (then measure `RANGE` by
  month);
- autovacuum on `messages` cannot keep up (dead-tuple growth in the collector's output);
- an owner deleting a large channel needs to finish in under about 0.5 s. The cheaper
  first step is to batch that delete like the expiry worker does, not to partition.

## Reproduce

```sh
cd server
# a disposable database whose name starts with d1_, migrated by this branch's code
DATABASE_URL=postgresql://user@host/d1_bench npx ts-node --project tsconfig.json db/postgres/index.ts
export P7_D1_DISPOSABLE_ACK=I_UNDERSTAND PG_URL=postgresql://user@host/d1_bench
O="--messages 6000000 --channels 50000 --servers 2000 --users 100000 --threads 50000 --thread-messages 500000"
node scripts/p7-d1-scale-benchmark.cjs populate $O
node scripts/p7-d1-scale-benchmark.cjs measure --table messages $O --json plain.json
node scripts/p7-d1-scale-benchmark.cjs build-hash $O
node scripts/p7-d1-scale-benchmark.cjs measure --table messages_h16 $O --json hash16.json
npx ts-node --project tsconfig.json scripts/p7-d1-erasure-probe.ts --json erasure.json
```

Both scripts refuse any database whose name does not start with `d1_`, and run only with
`P7_D1_DISPOSABLE_ACK=I_UNDERSTAND`.
