## New changes

- Realtime binds each ackId to the complete server/channel/content tuple in
  the same account epoch. Reusing an id with another payload fails with
  `IDEMPOTENCY_CONFLICT` before emission. Another account has a separate
  namespace. The ledger is bounded to 256 distinct IDs per epoch; additional
  new IDs fail explicitly with `IDEMPOTENCY_CAPACITY`, while existing exact
  replays remain possible. This pilot bound is not production throughput
  acceptance. Account transitions/disposal release retained payloads.
- Added real-backend scenarios to the existing PKCE integration file:
  authenticated A queues offline, sends with a stable ackId, deliberately drops
  the first actual server ACK, observes persisted history, reconnects, retries
  the identical tuple, then requires one canonical persisted message; and
  concurrent same-user same-id sends plus a different user using that same id.
  The tests use actual Socket.IO/HTTP and ordinary registration/PKCE helpers.
  No credentials, access checks or server responses are fabricated.
- Added a negative unit test for payload mismatch and account-scoped id reuse.

### Surviving coordinator mutation

Removing eager accessToken clearing in begin() does not bypass the public
getSession() guard: the phase is synchronously moved out of authenticated before
any callback/await and the epoch invalidates old work. The next authenticated
transition assigns a fresh token. This mutant is equivalent at the current
public API boundary, with a residual memory-hygiene distinction. There is no
demonstrated public token leak or reachable authorization defect from it.
Keep the eager clear for secret lifetime reduction. Do not expose private state
or assert source text merely to kill this mutant. Its SURVIVED score and campaign
exit 1 are retained; no 100% mutation score is claimed. A comment records this
independent defense, and the unchanged public transition tests continue to pass.
